# Jev はどこまで任せられるか：検証結果

[English](findings.md)

## 概要

**Jev は「コードを見れば答えが決まる質問」を 1 つずつ具体的に聞けば 9 割以上正しく答えるが、条件の組み合わせ・例に挙げていない種類・抽象的な質問では精度が落ちるため、質問を細かく具体的に分ければ、人や LLM が読む前の一次チェックとして使える。**

| | |
|---|---|
| 背景 | LLM にコードレビューを全部任せると、時間も費用もかかる。Jev は文章を書かずに「はい」の確率だけを返すので、1 回 0.3 秒・1 円未満で判定できる。 |
| 目的 | チェック項目を増やしたとき、種類が多岐にわたるとき、聞き方が抽象的なときに、Jev の判定がどこまで正しいかを確かめる。 |
| 方法 | わざと問題を 1 つ入れたコードと正常なコードを 72 件（10 言語・形式）用意し、正解を先に決めた。聞き方を 1 つずつ変えて Jev に判定させ、採点した。Jev の呼び出しは 2,578 回、費用は約 $0.36。 |
| 結果 | 1 つの事実を聞く質問は 99% 正しかった。観点を 387 個に増やしても精度は落ちなかった。条件を「かつ」で 4 つつなぐと 73%、例に挙げていない種類はほとんど見つけられず、抽象的な質問は関係ない問題にまで反応した。 |
| 結論 | 質問は「1 つのことだけ」「〜があるか の形で」「見つけたいものを名指しして」作る。Jev は怪しい場所の絞り込みに使い、最終判断は人か LLM が行う。 |

対象モデルは `jev-1.13.0`、検証日は 2026-09-23。

## 用語

- **p**: Jev が「はい」だと思う度合い（0〜1）。0.5 以上を「はい」とみなした。
- **拾えた割合（検出率・再現率）**: 本当に問題があるものを「はい」と言えた割合。
- **誤検知**: 問題のないものを「はい」と言ってしまうこと。

## 得意なこと

### 1 つの事実を聞けば、ほぼ確実に正しい

「return 文があるか」「ループがあるか」など、コードを見れば答えが決まる 16 の質問を 18 件のコードに聞いた。正解率は 99%。危険な呼び出し・秘密情報のような字面で分かる問題は、正しい質問の p が 0.97 だった。

### 観点をいくら増やしても、互いに邪魔しない

1 回の呼び出しに入れる質問を 6 個から 387 個まで増やしても、元の 6 項目の検出率は 89〜92%、応答は 0.3〜0.4 秒のままだった。増えるのは入力トークン（1 問あたり約 38）だけ。

### 何度聞いても同じ答えが返る

同じ入力を 3 回聞いたときのぶれは ±0.005〜0.013。3 回の平均を取っても検出率は上がらなかった。1 回で十分。

### 「ただし〜は除く」を理解する

例外を 0〜3 個付けても、本物の違反は p 0.96〜0.98 のまま見逃さなかった。例外に当たるコードは no にできた（テストの中の print: 0.97 → 0.15）。弱点は 2 つある。

- 当てはまる例外がリストの後ろにあると効きが落ちる（定数だけの連結: 先頭 0.26 → 最後 0.68）。
- **例外は、見た目の似た別のケースにまで効く。** 「Firebase の Web 用設定のように公開される前提のキーは除く」という例外を付けると、Swift に直書きした Google のキーまで 0.97 → 0.24 に下がった。「JavaScript の firebaseConfig オブジェクトの中の apiKey は除く」と目に見える目印で絞ると、Swift は 0.95 に戻り、Firebase は 0.12 のまま除外できた。

### 具体的な社内ルールなら、ルール文のまま判定できる

「課金 API を呼ぶ前に見積もりを入れること」など 7 本のルールを質問に入れた。7 本とも 0.5 を境に正しく分かれた。ただし抽象的なルールほど、無関係なコードでの p が上がる（具体的なルールで最大 0.11、抽象的なルールで最大 0.44）。

## 苦手なこと

### 条件を「かつ」でつなぐと、見落とす

全部そろっているコードを「はい」と言えた割合は、条件 1 個で 96%、2 個で 90%、3 個で 81%、4 個で 73%。入れ子（A かつ (B または C)）は 84%。同じ問題を 1 条件ずつ聞いてプログラムで組み合わせると、入れ子は 97%、全体では 95.3% → 97.9% に上がった。「どれか 1 つでも」（OR）だけは、まとめて聞いても 99.7% 正しかった。

### 例に挙げていない種類は、見つけられない

「eval・シェル実行・SQL 連結など危険な呼び出しがあるか」で聞くと、XSS のコードは p 0.04 だった。「innerHTML に差し込んでいるか」と名指しすると 0.94。言語別の検出率は TypeScript・SQL・Swift が 100%、Python 92%、JavaScript 80%、Dockerfile 50%、GitHub Actions 33%。落ちたのはどれも例に書いていない書き方（continue-on-error、curl | bash、`${{ github.event.* }}` の埋め込み）だった。

似た種類を細かく分けて聞く（SQL 注入・シェル注入・eval・XSS など 8 種）のは問題なかった。最も高い p が正しい種類だったのは 11 件中 10 件。ただし隣の種類にも同時に反応することがある。

### 抽象的に聞くと、何にでも反応する

「セキュリティ上の問題があるか」「費用のリスクがあるか」のような領域単位の質問は、別の種類の問題にも 35〜76% 反応した。「このまま本番にマージしてよいか」は、問題のあるコードを 1 度も通さなかった一方で、正常なコードの 47% も止めた。

### 「〜が無いか」と聞くと、ほぼ「はい」になる

「タイムアウトの指定が無いか」「説明コメントが無いか」のような質問は、正常なコードでも 77% が yes になった。「〜があるか」型は 3%。対象が差分内にあれば Jev は正しく no と答えたので、答え自体は誤りではない。変更部分だけを見ると、別の場所にあるものは写っていないので「無い」になる。

### 意味を理解しないと分からないバグ

ロジックの誤りを聞く質問は平均 p 0.65。期限切れ判定で不等号が逆（`expires_at > now`）のコードは、どの条件でも見逃した。

### 主観的な品質は、比べられるが合否は決められない

1 か所だけ違う良い版と悪い版を 8 組作った。「保守しやすいか」は 8 組すべてで良い版の方が高かった。しかし 0.5 で合否を切ると正解率は 54〜75% だった。

## 使うときの注意

- **差分はまとまりごとに渡す。** 無関係な文章を 2k トークン足すと 92% → 86%、28k まで足しても 89%。長い入力の真ん中に埋もれると 83%。急に崩れはしないが、少しずつ落ちる。
- **質問は 1 回にまとめて聞く。** 24 問を 1 回で聞くのと、6 問 × 4 回・4 問 × 6 回で聞くのとで検出率は同じ（89〜92%）。費用は 1.8 倍・2.4 倍になった。
- **確率の読み方。** p 0.9 以上は 97% が本当に「はい」だった。0.7〜0.9 は約 75%、0.5〜0.7 は約 48%、0.1 未満は 0%。赤の線を 0.5 から 0.7 に上げると、赤のうち本当に問題だった割合は 83% → 90%、問題を拾える割合は 90% → 81% になる。

## 質問を作るときのルール

1. 1 つの質問では、1 つのことだけを聞く。組み合わせはプログラムで行う（`[[rule]]`）。
2. 「〜があるか」の形で聞く。無いことの確認は、周りのコードを読める人か LLM に任せる。
3. 見つけたいものは、言語ごとの書き方まで名指しする。
4. 例外は「ただし〜は除く」で 3 個まで。いちばん効かせたいものを先頭に書き、ファイル名やオブジェクト名のような目に見える目印で範囲を絞る。
5. 抽象的な質問・主観的な質問で合否を決めない。
6. 変更は hunk ごとに渡し、質問は 1 回にまとめる。
7. 0.7 以上を赤、0.5〜0.7 を黄として扱う。最終判断は人か LLM が行う。

## この検証の限界

- 問題は自作の 72 件。実際のプロジェクトのコードでは結果が変わる可能性がある。
- 「名指しした質問」は、問題を見たあとに作ったので、実際より高めに出ている。
- 抽象的な社内ルールの違反例は、ルールごとに 1〜2 件しかない。
- 例外の実験のうち 3 件は、こちらの用意した正解より Jev の判断のほうが妥当だったため、採点から外した。
- 対象は `jev-1.13.0` のみ。

## 同梱の観点での実測

上のルールで書いた `core.ja` / `core.en`（15 項目）を、[samples/](../samples/) の 61 件で測った。

| | 赤（0.7 以上）で判定 | 黄（0.5 以上）も当たりとして判定 |
|---|---|---|
| core.ja | 61 件すべて正解（拾えた割合 100%、誤検知 0%） | 拾えた割合 100%、誤検知 0.5%（4 件、p 0.51〜0.67） |
| core.en | 61 件すべて正解（拾えた割合 100%、誤検知 0%） | 拾えた割合 100%、誤検知 0.2%（2 件、p 0.51〜0.55） |

サンプルは観点を書くときに参照した実験ケースと同じなので、この数字は上限と考えること。
